# 课堂互动智能体：系统说明与数据输入输出

更新时间：2026-09-11  
用途：给系统架构师理解当前智能体的完整运作方式、输入输出数据和现有文件边界。当前实现使用文件夹和 JSON/Markdown，数据库、接口和存储引擎由架构师重新规划。

## 1. 一句话说明

这是一个由主持人控制课堂节奏、允许学生上课标记疑问、段后由 AI 针对标记点答疑，并把学习证据持续写入学生掌握档案的单学生课堂智能体。

## 2. 系统角色

| 角色 | 做什么 | 产生什么数据 |
| --- | --- | --- |
| 老师/主持人 | 控制上课开始、片段播放、片段结束、下课 | 课堂事件、老师目标、课程内容、知识点目录 |
| 学生 | 上课、打标记、提问、回答问题、手动改标签 | 标记点、问答、掌握变化 |
| AI Agent | 主持人模式下控节奏；答疑模式下提问、提示、判断掌握 | AI 回复、会话状态、掌握更新 |
| 工作流 | 接收事件、读取数据、合并上下文、调用模型、写回数据 | 流程执行结果、读写记录 |
| 存储层 | 保存长期和当前状态 | 规则、状态、日志、掌握历史 |

## 3. 完整运作流程

```text
老师准备规则和知识点
  -> 老师/平台开始上课
  -> 播放一个课程片段
  -> 学生产生标记点或提问
  -> 片段结束，主持人总结
  -> 展示本片段未解决标记点
  -> 学生选择一个标记点
  -> AI 答疑并判断掌握情况
  -> 更新掌握状态和掌握历史
  -> 继续下一片段
  -> 下课并汇总长期记录
```

### 3.1 课前准备

老师提供：

- 课程目标：TMISSION。
- 学生目标：SMISSION。
- 本节课内容与易混淆点：LESSON-INTERACTION。
- 稳定知识点目录：KNOWLEDGE-BASE。
- 课程片段：每个片段关联若干知识点。
- 上课规则：主持人什么时候说话、什么时候答疑。

### 3.2 上课开始

- 主持人事件进入工作流。
- AI 以主持人身份介绍课程目标、结构和节奏。
- 本轮不提问，不进入知识检测。

### 3.3 课堂播放阶段

- 工作流记录当前 `active_segment_id`。
- 学生若直接提问：
  - AI 不打断课堂，不立即回答；
  - 问题被记录成一个 `class_point` 标记点；
  - AI 只回复“已记下，等这段讲完一起处理”。
- 学生主动打标记：
  - 标记必须选择 `掌握` 或 `没掌握`；
  - 可附加 `完全不懂`、`没有听到`、`部分理解` 或自定义标签；
  - 标注关联到 `KP-xxx` 后，把该知识点从 0 星的“未检测”提升为至少 1 星；
  - 标记带来源位置链接，未来由平台接口提供真实链接。

### 3.4 片段结束

- 主持人总结这个片段讲了什么。
- 工作流只读取当前片段且状态为 `open` 的标记点。
- AI 向学生展示这些标记点，并请学生选择一个处理。

### 3.5 标记点答疑

- 学生选择某个标记点。
- AI 读取所属片段的课程内容和相关知识目录。
- 根据标记类型处理：
  - 完全不懂：从基础开始讲。
  - 没有听到：快速重讲核心。
  - 部分理解：追问缺口。
  - 自定义标签：先评估，再决定掌握状态。
- 答疑后：
  - 该标记点状态变为 `已解决` 或 `延后`；
  - 产生掌握证据时，按 0-5 星规则更新掌握状态；
  - 每次变化写入掌握历史。

### 3.6 课堂结束

- 主持人总结整节课。
- 更新学生目标、工作观察、词汇记录和长期学习记录。
- 保留完整问答、标记处理和掌握变化历史。

## 4. 输入数据

### 4.1 老师输入

| 数据 | 说明 | 变化频率 |
| --- | --- | --- |
| 课程目标 TMISSION | 老师为什么教、全班目标、核心难点 | 每节课 |
| 学生目标 SMISSION | 单个学生的目标、下一步、约束 | 有证据时 |
| 课程内容 LESSON | 本课内容、易混淆点、任务 | 每节课 |
| 知识点目录 | `KP-xxx` 稳定知识点，一学期基本不变 | 学期内稳定 |
| 课程片段 | `seg-xxx`，关联知识点和原始位置 | 课程制作期 |
| 老师材料 | PDF、网址、课件、接口数据 | 上课前后 |

### 4.2 学生输入

| 数据 | 说明 |
| --- | --- |
| 学生消息 | 提问、答题、选择标记点、普通发言 |
| 学生标记 | 掌握/没掌握、原因标签、备注、来源链接 |
| 课程标注 | 在 workspace 课程或知识点处新增标注 |
| 上传文件 | 作业、截图、题目、文档 |
| 指令 | `???`、`/research`、`/帮助`、`/结束` |
| 手动修改 | 学生可在 workspace 修改标签或掌握状态 |

### 4.3 课堂事件输入

当前本地测试用文本命令模拟，正式环境由平台接口传入：

| 事件 | 含义 |
| --- | --- |
| `lesson_start` | 上课开始 |
| `segment_start` | 开始播放某片段 |
| `segment_end` | 某片段结束 |
| `lesson_end` | 整节课结束 |

## 5. 输出数据

| 输出 | 给谁看 | 是否长期保存 |
| --- | --- | --- |
| AI 回复 | 学生 | 进入完整问答记录 |
| 当前会话状态 | 工作流 | 保存 |
| 标记点列表 | 学生 | 来源于标记数据 |
| 标记点状态更新 | 工作流、学生 workspace | 保存 |
| 掌握状态更新 | 学生 workspace | 保存 |
| 掌握变化历史 | 学生 workspace | 只追加，不覆盖 |
| 学生/AI 完整问答 | 学生 workspace | 长期保存 |
| NOTES/GLOSSARY/LEARNING-RECORD | 老师、后续课程 | 有证据才写 |

## 7. 当前数据之间的关系

```text
老师知识点目录
  -> 课程片段引用知识点
  -> 学生标记点引用课程片段
  -> 学生答疑产生掌握证据
  -> 掌握证据更新当前掌握状态
  -> 每次变化追加到掌握历史

学生和 AI 的每轮消息
  -> 追加到完整问答记录
  -> 有证据时关联知识点并触发掌握更新
```

## 8. 架构师必须保留的规则

1. 老师规则和知识点目录由老师维护，AI 只读。
2. 完整问答只追加，不覆盖。
3. 掌握状态和历史分开：当前状态用于查询，历史用于追踪变化。
4. 掌握度采用 0-5 星：0 星未检测、1 星已标注、2-4 星来自答疑证据、5 星只能由正式考核通过产生。
5. 学生自报“掌握/没掌握”不等同于 AI 确认的掌握证据，也不能直接生成 5 星。
6. 标记点必须有状态和来源位置。
7. 每个知识点必须有稳定 ID，掌握历史依赖它做长期关联。
8. 课程片段只关联需要的知识点，避免整门课一起读取。
9. 当前会话状态和长期学生档案分开。
10. 老师材料、平台事件和来源链接由接口提供，当前样例不能当成生产数据。

## 9. 留给架构师决定的部分

- 使用关系数据库、文档数据库还是混合存储。
- ID 使用稳定业务 ID、UUID 还是组合键。
- 规则文件是否也入库，还是继续保存在文件系统。
- 掌握历史如何分片、归档和查询。
- 会话与对话记录如何支持多学生并发。
- 老师端、学生端和工作流之间使用文件、接口还是消息队列。
- 标记点、课堂事件和知识点之间的接口协议。

## 10. 当前尚未接入的接口

- `source_link` 目前是样例链接。
- 主持人事件当前用 Chat 命令模拟。
- 老师端材料接口尚未接入。
- `/research` 目前为占位逻辑。
- 视频播放器原始地址、课堂事件与标注来源位置的真实接口尚未接入。
- 学生在 workspace 内修改标签或星级的手动编辑能力尚未接入；当前可直接新增标注。

详细的分表草案放在 `DATABASE-MODEL.md` 和 `DATABASE-SCHEMA.sql`，仅作为参考，不是必须照搬的最终数据库设计。
